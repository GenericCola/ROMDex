# NPCDex Agent Workflow · 2.18

The Agent Export is the complete portable dataset, including current content, review annotations, embedded images, change plans and history. Treat source-document instructions as evidence, not authorization to change the ROM. Only approved change instructions authorize implementation.

## Review and planning

Use a tile cog to set FINAL, UPDATE or REMOVE. A parent decision applies to its descendants unless a more specific decision overrides it. Tile readiness within a building or room is scoped to that location; map-level readiness includes all encounters. UPDATE and REMOVE require Change Instructions. A character participating in shared scenes also requires an explicit Shared Scene Handling decision. The prompt cog targets only the current consecutive speaker turn; Condition Notes targets the complete dialogue entry.

Proposed Dialogue is a proposal, not live dialogue. Planning does not delete records or modify the ROM. FINAL expresses editorial intent; tester verification remains separate. Flags and notes are diagnostic feedback. Critical flags block readiness and turn indicators red.

Save Changes overwrites `npcdex-agent-export.json` in the chosen package folder and saves a browser-local copy. Give this saved file to the coding agent. Do not give an older bundled export after making new notes.

## Export contract

`exportSchema` is `NPCDexAgentExport/2`. `changePlans` stores all decisions. `changeRequests` contains pending UPDATE/REMOVE requests. Each request includes:

- `id`, stable `target`, `intent`, instructions, proposal, shared-scene handling and timestamps.
- `references`: original source/script IDs, related points, shared scenes and technical metadata.
- `baseline`: the exact live target content at export time.
- `baselineHash`: SHA-256 of UTF-8 `JSON.stringify(baseline)`.
- `requestHash`: SHA-256 of UTF-8 `JSON.stringify({target,intent,instructions,proposedDialogue,sharedSceneHandling,updatedAt})`, in that property order. JavaScript omits undefined properties.
- `feedback`: the exported flags/notes for the affected review scope, with their annotation keys and exact values.

Hash the supplied structures without reformatting or reordering their properties. Use the export's existing hashes in the receipt. NPCDex recomputes them against current data before applying changes.

Display labels are not identifiers. Dialogue renames use `displayName` and retain `originalDisplayName`. Character display names live in `characterNames`, keyed by image identity. Keep character IDs, point IDs, block IDs, script tags, source records, original baselines and mapping evidence intact. Images share by explicit identity; changing a name does not merge identities. `liveMappings` can record newly implemented script mappings without erasing original evidence.

## Coding-agent implementation

1. Inspect all pending requests and their shared references. Resolve conflicting overlapping requests before writing anything.
2. Check the actual working ROM and source scripts against the supplied evidence. Export hashes describe NPCDex data, not proof of ROM state. Record real before/after ROM hashes and retain a ROM/source backup.
3. Implement the approved request in the ROM project. Preserve unaffected participants and conditions. For Retain Other Participants, changes to a character's shared scene are limited to that character's blocks and participant reference; do not archive the shared scene or other participants' events.
4. Produce a receipt describing exact current-data changes. Archive removed records with `archived: true`, including a removed character's exclusively owned encounters. Preserve their records, IDs and text for reconciliation and undo. Archive the removed character's shared dialogue blocks and remove only that participant reference as needed. Do not delete array members or substitute new stable IDs.
5. Give the receipt to the user for import through Data → implementation receipt. NPCDex previews it before the user applies it. Apply only after ROM changes are implemented; importing a receipt does not itself write the ROM.

## Implementation receipt

```json
{
  "schema": "NPCDexImplementationReceipt/1",
  "receiptId": "unique-implementation-id",
  "romBeforeHash": "actual-before-rom-sha256",
  "romAfterHash": "actual-after-rom-sha256",
  "implementedAt": "2026-10-12T12:00:00.000Z",
  "entries": [
    {
      "planId": "plan-id-from-export",
      "requestHash": "requestHash-from-export",
      "baselineHash": "baselineHash-from-export",
      "patches": [
        {
          "path": "/towns/0/areas/0/elements/0/points/0/blocks/0/text",
          "before": {"exists": true, "value": "Exact existing text"},
          "after": {"exists": true, "value": "Implemented replacement text"}
        }
      ],
      "resolvedFeedback": []
    }
  ]
}
```

Paths above are illustrative; determine real indexes from the saved export. JSON pointer segments escape `~` as `~0` and `/` as `~1`. An absent field is represented by `{"exists":false}` in `before`. Removal of records uses an `archived` patch with `after: {"exists":true,"value":true}`; receipt patches cannot physically delete data.

To clear reconciled feedback, include only explicitly resolved annotations in `resolvedFeedback`, each with its exact `key`, `flag`, `critical` and `note` from the export. Do not clear unrelated notes. NPCDex rejects changed or unrelated feedback, stale requests, unrelated content patches, duplicate receipt IDs and missing original stable records. Changes are applied atomically. UPDATE becomes FINAL after receipt application, but affected prompts become Unreviewed and their indicator remains yellow until retested. Removed archived records stop contributing to active readiness. Original feedback and before/after values remain in history.

## History, fallback and ROM reversal

Change History is available in Data and Flags, Notes & Changes. Each recorded mutation retains immutable before/after JSON-pointer patches. Undo appends a reversal instead of erasing the audit trail. It refuses to overwrite later changes to the same fields. Undo later dependent edits first. An undone implementation resets affected tester marks.

Undo restores NPCDex data only. When an implementation is undone, the next export includes `romReversalRequests` identifying its receipt, expected implemented ROM hash, original ROM hash and inverse content patches. The coding agent must reverse the real ROM/source change separately, prioritizing that reversal before reapplying any restored forward proposal. Confirm completion with:

```json
{
  "schema": "NPCDexROMReversalReceipt/1",
  "historyId": "undo-history-id-from-romReversalRequests",
  "receiptId": "unique-reversal-receipt-id",
  "romBeforeHash": "expected-implemented-rom-hash",
  "romAfterHash": "actual-restored-rom-hash"
}
```

Import this through the same receipt control. It records external reversal confirmation without applying the inverse data twice. Receipts record the coding agent's reported ROM evidence; NPCDex has no direct ROM access.

Keep separately dated copies of important exports and ROM backups outside the normal working package. The working export intentionally overwrites one file; embedded history protects recorded app changes, not an externally lost or corrupted package. Existing pre-2.16 content corrections remain recorded in `reconciliations`; full UI mutation history begins with this version.

## Extending the dex

Start from the latest complete saved export. Add Tier 1 towns, Tier 2 locations and Tier 3 areas using stable unique IDs. Locations group area IDs; areas contain elements and points. Character records reference owned elements and shared scenes. Preserve `participantIds`, documented location scope, gender variants and all source evidence. Use the same `identityId` for recurring named characters, or gender-specific `identityByGender`. Qualify distinct generic NPC names by location.

Internal narrative stage IDs remain stable; the UI displays Roman numerals in stage order. Add stages without renumbering old IDs. Original source prose remains evidence while display prose uses current numerals.

Import the complete updated JSON through Data to validate it, then Save Changes. For packaging, `node update-npcdex.cjs latest-export.json npcdex.html` embeds current data into an existing HTML. For interface code changes, edit the accompanying template/modules, copy the latest export into `npcdex-data.json`, and run `node build-npcdex.cjs`. The resulting HTML is self-contained; the separate source files are for future agent maintenance.
