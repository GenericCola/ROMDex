# Versioned Content Editing — U20D–U20E

U20D extends the U20C reader with an owner-only edit journal, publication writer and editing controls. U20E also binds the editor to the accepted native content workspace after a verified migration handoff. Before that handoff the established GitHub-backed provider remains authoritative. No PMON task creation, agent dispatch or implementation acceptance is enabled by these commands.

## Domain Boundaries

`edits.mjs` builds supported commands from a pinned local head and immutable record versions. Ordinary plans, proposed dialogue, proposed pictures, notes and testing observations are separate artifacts. They never replace current content. Ready UPDATE/REMOVE/ADD proposals require nonblank instructions and a concrete scoped change; instructions-only drafts and editorial FINAL decisions are not executable work packages. Assets required by a proposal are versioned without changing the character's current picture.

Add Character creates a `planned` appearance, optionally a new shared profile, and its parent's membership revision as one complete publication. An existing shared profile can be reused with a local display-name override. Shared identity and player-gender profile overrides remain explicit; sprite/name similarity does not infer identity. Planned records may be archived. Planning and documentation corrections cannot activate a Planned Addition, including one archived earlier. Activation needs later implementation evidence.

Documentation Correction is a distinct owner action requiring reason and evidence. It retains before/after references, identity, mapping and compatibility data. A shared-profile correction requires acknowledgment of its shared scope and advances affected appearance/scene revisions so old testing displays Unreviewed; original observations and all newer plans remain preserved. Local overrides do not overwrite the shared profile. Existing-content archival/restoration requires this explicit correction intent and a valid complete dependency graph. It describes recorded ROM content; it does not execute ROM changes. Proposed removals remain REMOVE plans. Archived records remain available in the correction/testing record selectors; physical deletion and ROM reversal are not editing operations.

## Durable Intent and Publication

`writer.mjs` persists the immutable publication, artifacts, assets and local preview before network requests. SQLite transactions protect the journal. Offline edits use their original semantic baseline and survive restart. The view distinguishes local pending work from acknowledged remote content. Auto-Sync Off performs no automatic remote reads or writes; manual Save runs one incoming/outgoing cycle and leaves Off in place.

Before publishing, the editor reads the current registry. A changed baseline blocks the old operation for review, retaining its exact original artifacts. It never silently rebases a correction or substitutes newer text. Each issue/upload attempt is recorded before sending. After an interrupted response, the next cycle searches the exact operation/record identity or expected filename/length/bytes under the pinned issue. Confirmed accepted bytes are reused. An unresolved attempt is not blindly repeated; the review pane allows an explicit reviewed retry. Duplicate record identities or conflicting immutable bytes are held for review.

New issue IDs, links and object chunks are established and verified before the registry carrier is appended last. A carrier pins complete bindings, hashes, author policy and native metadata. Published operations are acknowledged only through the reader's verified ancestry. A successful HTTP response alone does not certify a complete content update. Partially created issues/files are retained for recovery, not silently deleted or dispatched. Cancelling eligible local work retains its journal history; already published or uncertain operations cannot be erased through Cancel.

`youtrack-writer.mjs` permits an isolated `fixture:` context or the explicitly accepted U20E content workspace. Both pin NPCD project `0-2`, owner `2-2`, their exact marker and a marked private registry. Accepted initial registry creation is allowed only in an empty NPCD project or by rediscovering the exact frozen import registry. Every target issue is checked for its project, reporter, marker, summary prefix and owner-only explicit visibility. The writer exposes only the reviewed create/upload/parent-link operations; it has no PMON, comment, task-State, account, permission or deletion operation. Existing trusted administrators may still access restricted issues. Actual agent permissions remain U23.

Signed attachment URLs remain inside the transport and are not written to the journal, projection or packages. Stable issue/attachment IDs and verified hashes are durable references. Original authoritative saves and all three protected credentials remain outside development archives.

## Conflict Recovery

The reader handles publication ancestry as a DAG. Concurrent heads retain both branches and display their verified common ancestor. An explicit resolution names exactly the observed heads, reviews their baselines and selects an observed current revision for each conflicting record. All records, version histories, plans, notes, mappings and assets survive the join. It cannot invent an unobserved current value or discard a new record. Graph validation refuses incompatible membership/participant choices.

Drafts with the same plan/review identity retain every concurrent head. After joining publications, editing that draft must cover every current draft head; the UI requires acknowledgment of the displayed versions. A newly discovered branch is not covered by an earlier resolution. Ordinary cancellation/recreation of blocked offline edits is explicit and retains the original journal artifacts. No timestamp, filename, task State or actor claim chooses a winner.

## Preview and Bounds

The optional editor in `preview-server.mjs` adds bounded, same-origin loopback edit/draft/recovery routes. The native service reuses the reader/editor directly; it does not run the loopback preview server. Native editing uses a bounded application command facade and service events rather than browser polling. Forms use the familiar NPCDex presentation with separate Plan Changes, Flags & Notes, Correct Documentation, Add Character and Review Sync controls. Legacy mutation/storage handlers remain disabled. Incoming refresh does not repaint an open form. Versioned local drafts, including selected picture bytes, can be resumed; stale heads or competing draft writes require review rather than silently overwriting either version.

Outgoing synchronization has a ten-minute transport deadline, a 200-write budget and a maximum of 20 queued operations per cycle. Original intents survive a bounded cycle ending before completion. Edit requests and draft uploads are limited to 1 MiB. Images are limited to 512 KiB, supported raster signatures and bounded dimensions (at most 4096 per side and 8 megapixels); these checks are not a full image-file conformance proof. U20E preparation permits a 512 KiB carrier within the previously proved upload bound, shares immutable domain bodies and bounds network concurrency to four. The active journal allows 200 pending operations plus 32 recent terminal operations; older terminal entries are archived with original previews/intents. There is no 200-edit lifetime cap and no automatic remote-history deletion. Routine polls inspect fresh metadata/inventories; manual saves and 15-minute full audits reread bytes. Larger-data retention, history projection, native-edit adoption and complete real-save mapping need the U20E/U20F proofs. Server upload ceiling and remaining storage are still unknown.

U20E requires a fresh capture/preview and user acceptance before switching to one authoritative content provider. U20F verifies installed behavior. U21 packages/attaches map changes by explicit user choice. Agent-authored implementation and testing/completion gates remain U23–U27.


Original migration evidence is not editable content. The native content picker excludes that technical record, and command validation rejects attempts to stage plans, reviews or corrections against it. Complete original bytes remain independently recoverable and retain their source hash. Migration does not certify ROM locators, execute instructions, dispatch agents or mark implementation work tested.
